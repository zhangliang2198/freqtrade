## 1. 执行摘要

这是一套**工程质量明显高于普通用户策略**的代码：数据因果性、K 线新鲜度校验、轮换状态机、审计幂等、文档与公式一致性都做得扎实。README 里的示例评分（44.6 / 62.0）我用 `_apply_scores` 的公式逐项复算，完全吻合。

问题不在"算错了"，而在三件事：

1. **风险预算过大且没有组合级熔断**——单笔止损等于该笔全部保证金 = **8% 账户权益**，10 仓高度相关，`account_stopped` 被硬编码为 `False`。
2. **退出决策的全部逻辑放在会被框架静默吞掉异常的回调里**——`custom_exit` 抛异常 = 不退出（只有一行日志）。这属于"能正常工作时很好、出意外时无声失效"的结构。
3. **没有任何历史验证**——回测/Hyperopt 被显式拒绝，约 120 个手调参数，而承载"挤空"论点的两个因子（强平、OI）恰好没有历史数据源。

### 1.1 风险仪表盘

| 维度 | 评级 | 说明 |
|---|---|---|
| 单笔风险 | 🔴 高 | 8% 权益/笔（`stake_ratio 0.08` × `stoploss -1.0`） |
| 组合风险 | 🔴 高 | 10 仓 × 8% = 80% 保证金，全仓共担抵押，无回撤熔断 |
| 相关性风险 | 🔴 高 | 标的来自同一个"15m 涨幅榜前 50"，高 beta 同涨同跌 |
| 尾部风险 | 🟠 中高 | `stoploss=-1` + 交易所止损，官方文档明确警告可能挂单失败 |
| 退出可靠性 | 🟠 中高 | 异常被 `default_retval=False` 吞掉；退出无滑点检查 |
| 逻辑一致性 | 🟠 中 | 排序用 ≤900s 旧评分，硬门槛用最新 K 线 |
| 数据正确性 | 🟢 好 | 无未来函数，闭 K 线校验严格，缺数据即禁止开仓 |
| 实现健壮性 | 🟢 好 | 状态机自洽、审计幂等、损坏状态文件保守处理 |
| 可维护性 | 🟠 中 | 5292 行、约 120 个参数、依赖私有 fork |
| 实证支持 | 🔴 无 | 无回测、无样本外验证 |

### 1.2 结论一句话

**19 条核查项中 17 条成立、1 条降级（性能）、1 条撤回（我自己复核时的误判），另有 2 条新增。** 优先处理：单笔风险预算（S-01）、退出兜底（C-01/S-02）、fork 绑定（P-01）。

```

FreqtradeBot.process()
 ├─ pairlist 刷新 → 动态白名单（VolumePairList 200 → 过滤器 → PercentChangePairList 前 50）
 ├─ dataprovider.refresh()                     ← 拉 15m K 线（Binance 单次 499 根）
 ├─ strategy.bot_loop_start()   [strategy.py:494]  ← @decision_snapshot 缓存作用域
 │    ├─ 仓位同步（30s 一次，同步 REST fetch_positions）
 │    ├─ ETH 过滤（15m + 1h EMA/ATR/结构）
 │    ├─ _update_market_state()  普跌/急跌宽度   [strategy.py:573]
 │    ├─ _consume_score_refresh() 合并后台指标   [helpers.py:989]
 │    ├─ _start_score_refresh() 触发后台线程（900s 一轮）
 │    ├─ _refresh_risk_state() → 每轮写状态文件  [strategy.py:2096]
 │    ├─ _sync_rotation_state() / _plan_rotation()
 │    ├─ _select_entries() 入场漏斗             [strategy.py:1073]
```

### C-01 [P0] 退出与选币回调整体被框架静默吞异常

**证据**
- `freqtrade/strategy/interface.py:1484`：`strategy_safe_wrapper(self.custom_exit, default_retval=False)`
- `freqtrade/freqtradebot.py:338`：`strategy_safe_wrapper(self.strategy.bot_loop_start, supress_error=True)`
- `freqtrade/strategy/strategy_wrapper.py:31-60`（`strategy_safe_wrapper`）：任何异常 → 记日志 → 返回 `default_retval`
- `leader_squeeze_strategy.py:453-491`：`custom_exit` 承担**全部**主动退出决策
- `leader_squeeze_strategy.py:467`：对每个持仓每轮调用 `_trend_reversed(pair)`

**机制**：`custom_exit` 内任何未预期异常（数据字段缺失、状态文件异常、第三方接口异常、未来重构引入的错误）都会被转换成"返回 `False`"，即**不退出**。持仓会一路持有到 −20% 价格的硬止损。

**影响**：这是"安全关键代码 + 全局异常吞噬"的组合。静态看很难发现，运行期只有一行 `Unexpected error ... calling custom_exit`。同理 `bot_loop_start` 抛异常会导致 `_entry_pairs`、轮换状态、风控统计静默停留在上一轮。

**建议**
1. 在 `custom_exit` 函数体内部自己包 `try/except`，异常时：
   - `logger.error` 带完整上下文；
   - 设置"趋势评估不可用"标志；
   - 返回 `None`（不退出）但**计数**。
2. 增加兜底规则：连续 N 轮（建议 6 轮 ≈ 30s）无法完成趋势评估 → 减仓/退出，而不是无限持有。
3. 给 `bot_loop_start` 内部的关键阶段（风控状态、轮换状态同步）各加独立 `try/except`，避免一处异常跳过后续全部阶段。

**状态**：✅ 已验证（框架行为 + 代码路径）

|---|---|
| `_trend_reversed` 中位数 | **24 ms** |
| p95 | 72 ms |
| 最大值 | **152 ms** |

### C-03 [P0] 排序用旧评分，硬门槛用最新 K 线（时间基准不一致）

**证据**
- `leader_squeeze_strategy.py:681-688`：`_current_score()` = `_scores[pair] + 资金费修正`，**只**重算资金费项
- `config.json:52`：`score_refresh_seconds = 900`
- `leader_squeeze_helpers.py:1009-1012`：下一轮刷新 = `min(now+900, max(now+30, deadline−30))`
- `leader_squeeze_strategy.py:1171-1178`：硬门槛用 `_candle_metrics(pair)`（**每轮最新已收盘 K 线**）重算动量/连续性
- `leader_squeeze_strategy.py:1225-1247`（`_entries_allowed`）：`max_age = score_refresh_seconds + data_grace_seconds` = 900 + 30 = 930s

**机制**：一个币的**排名**与**逐仓强度门槛**由最长约 15 分钟前的 42% 权重动量分决定；而**是否允许入场**由最新一根 K 线决定。结果是"只要现在动量刚刚 > 0、最近 3 根里 2 根涨"，一个 15 分钟前的高分币仍可入场。

**影响**：在快速轮动的龙头行情里，这等于给衰减的龙头保留了旧排名，抬高误入场概率。

**建议（低改动优先）**
- 在选币和 `confirm_trade_entry` 复核时，用最新 K 线重算 momentum / volume / taker 三项核心分（数据现成，成本低），把 `_current_score` 变成"基础分骨架 + 实时核心项"。
- 或把综合分的有效期从 900s 收紧到 1 根 K 线（15m）。

**状态**：✅ 已验证

### C-04 [P1] 入场选币阶段串行请求盘口，阻塞主线程

**证据**
- `leader_squeeze_strategy.py:1022`：`self._execution_is_safe(pair)`（`cached_only` 默认 `False`）
- `leader_squeeze_helpers.py:1788`：`_execution_is_safe`；`:1768`：`_execution_order_book`（TTL = `order_book_max_age_seconds = 5s`）
- `leader_squeeze_strategy.py:1006-1009`：容量已满时提前 `continue`（所以上限是 `capacity`）

**机制**：盘口缓存 5s、主循环也是 5s → 基本每轮失效。每个通过强度门槛的候选触发一次**同步** 20 档盘口 REST 请求，直到名额填满。最多 `capacity`（≤10）次/轮。

**影响**：主线程阻塞约 0.5–1.5 s/轮（每次 50–150 ms 估算），并持续占用 Binance depth 权重；且这段发生在 `custom_exit` 之前，等于挤占退出处理时间。

**建议**
- 选币阶段用 `cached_only=True`，只对最终入选的 ≤`capacity` 个做盘口复核；
- 把盘口 TTL 提到略大于循环间隔（如 8–10s）；
- 或并发取盘口（`metric_workers` 已有线程池基建）。

**状态**：✅ 已验证（请求次数上界由代码保证；耗时为主观估算，未实测网络）

### C-05 [P1] `_fetch_pair_metrics` 的"保留旧缓存"分支不可达

**证据**
- `leader_squeeze_helpers.py:1332`：`exit_metric: dict[str, float] = {}`
- `:1337-1350`：taker 请求/解析、OI 请求、数值校验（任一失败都会进 `except`，此时 `exit_metric` 仍为 `{}`）
- `:1351-1357`：`exit_metric` **只在这里**被赋值
- `:1361-1363`：`if not self._metrics_current(exit_metric, ...): raise`
- `:1374-1384`：`_metrics_current({})` → `all(...)` 空键 → `False`

**机制**：由于 `exit_metric` 只在两个请求都成功之后才赋值，`except` 里对它的检查恒为 `False`，所以总是 `raise`。而日志（`:1364-1369`）声称"仅保留有效 OI/主动买卖缓存, 不用于评分开仓"，与实际行为不符。

**影响**：taker 或 OI **任一**失败 → 该币丢掉**全部**指标（而不是复用旧缓存），进而拉低覆盖率、暂停开仓。诊断日志会误导排查方向。

**建议**：要么实现真正的部分复用（先取旧缓存再补新数据），要么删除该分支与误导性日志，改为明确记录"部分指标失败 → 该币本轮不计分"。

**状态**：✅ 已验证（逐路径追踪；`_metrics_current({}) == False` 已由代码逻辑确认）

### C-06 [P2] `_clamp` 遇到 NaN 返回满分 1.0

**证据**
- `leader_squeeze_strategy.py:562-563`：`return max(low, min(high, value))`
- 实测：`max(0.0, min(1.0, float('nan'))) == 1.0`（Python `min` 的比较语义：`nan < 1.0` 为 `False`，保留 `1.0`）

**影响**：任何 NaN 输入都会得到**满分**而不是最低分。当前唯一可能入口是 `_fast_rotation_quality` 里的 `taker`（`leader_squeeze_strategy.py:1616-1622`），且它同时受 `taker_aligned` 约束（`:1617`），所以**目前不影响开仓/轮换判定**，但这是典型的"NaN 变成奖励"的反向失效模式，未来改动很容易踩中。

**建议**
```python
@staticmethod
def _clamp(value: float, low: float = 0.0, high: float = 1.0) -> float:
    if not math.isfinite(value):
        return low
    return max(low, min(high, value))
```

**状态**：✅ 已验证（行为实测；"当前不影响判定"为代码推断）

| 方案 | `stake_ratio` | `stoploss`（保证金%） | 对应价格幅度（5x） | 每笔风险 |
|---|---|---|---|---|
| A 收紧止损 | 0.08 | −0.125 | −2.5% | 1.0% |
| B 缩小仓位 | 0.02 | −0.5 | −10% | 1.0% |
| C 折中 | 0.04 | −0.3 | −6% | 1.2% |

## 附录 D. 盈利保护设计与实现

> 对应审查项 **S-03/S-04**。本节记录诊断、取舍、已落地的代码、单位口径的实测依据，以及**如何用数据决定后续要不要继续加码**。

### D.1 诊断：现有"移动止损"不是盈利保护

策略已经有一个 trailing exit，但它**锚在 1h 枢轴结构上**：支撑 = 最近约 20 根 1h 的最低枢轴低点，退出价 ≈ 支撑 − `reversal_atr_buffer × ATR1h`。这带来一个结构性后果：

**回吐量随盈利规模增长。** 一个已经浮盈 +25% 的仓位，只要 1h 结构还没破，可以一路回吐到 −5% 才触发退出。1h 级别的枢轴支撑对已经走完主升段的龙头来说太远了。

缺的不是"止盈"，而是**棘轮（ratchet）**：一条只向上移动、永不回退的止损线。这与 `stoploss=-1.0`（价格 −20%，5x 下等于亏光该笔全部保证金）形成对照——灾难止损保护的是账户，不是利润。

### D.2 四层方案与取舍

| 层 | 规则 | 实现通道 | 结论 |
|---|---|---|---|
| **L1 保本棘轮** | 峰值浮盈 ≥ 1R → 止损推到成本价 + 费用缓冲 | `custom_stoploss` | ✅ 已实现 |
| **L2 R 跟踪** | 峰值达到 1R 后，止损 = `max(费用地板, 峰值 − 1.5R)` | 同 L1（同一函数） | ✅ 已实现并启用 |
| **L3 回吐保护** | 浮盈回吐 > `max(1R, 峰值的 40%)` 即退出 | `custom_exit` | ⏸ 未实现（与 L1/L2 功能重叠，先看数据） |
| **L4 动量/时间止损** | 8 根 1h 未累计推进 0.25R + 趋势明确走弱 + 浮盈低于 0.5R → 退出 | `custom_exit` | ✅ 已实现并启用 |
| ~~部分止盈~~ | 到某涨幅减半仓 | `adjust_trade_position` | ❌ **主动否决** |

**为什么否决部分止盈：**
1. **砍掉右尾**。这个策略的期望值来自少数几只走 3–10 倍的龙头，减半仓等于把最大的那部分收益让出去。
2. **破坏轮换对账**。`_rotation_trade_filled` / `_sync_rotation_state` 假定整仓换整仓，部分成交会让 `amount` 与交易所实际持仓漂移。
3. **需要开新开关**。`position_adjustment_enable` 目前是 `false`，开启会引入一整条新的下单/对账路径，风险远大于收益。

### D.3 L4 的独立职责：处理缓慢失速

**论点死了就该走。** 这套策略买的是"龙头动量 + 挤空"，如果入场后连续 8 根 1h 没有累计推进至少 0.25R、且 1h 趋势已经明确走弱，那么买入理由本身已经不成立——继续持有只是在赌。

关键在于**复用已有的判定**：`_no_new_high` 早已存在（`helpers.py` 的 `LeaderTrendMixin._no_new_high`，原先只用于**相对**轮换比较"弱不弱"）。把它提升为**绝对**退出条件，逻辑不变、语义更强。这也顺带解决了 S-04（"浮亏达保证金 X% 的兜底退出"）——一个不创新高的仓位通常也赚不到钱。

### D.4 单位口径（已用真实 `Trade` 实测，非文档推算）

这是最容易写错的地方。官方文档里 `trailing_stop_positive = 0.02 → 2%` 的例子**隐含 `leverage = 1`**。在本策略 5x 下：

| 期望的价格距离 `d` | `custom_stoploss` 应返回 | 实测结果 |
|---|---|---|
| 止损价 = 当前价 −1.0% | `d × leverage = 0.05` | 框架把 stop 放在 100.98（entry 100）✅ |
| 止损价 = 100.15，当前价 108 | `stoploss_from_absolute(100.15, 108, leverage=5)` = 0.363426 | `adjust_stop_loss` 后 `trade.stop_loss = 100.1500` ✅ |

因此代码**不手工折算**，统一调用官方 helper：

```python
value = stoploss_from_absolute(target_price, current_rate, is_short=False, leverage=trade.leverage)
```

同理，`custom_roi` / `calc_profit_ratio` 都是**保证金口径（已含杠杆放大）**：价格 +1% → `0.05`，+10% → `0.50`。所以本模块里所有 `profit_ratio` 都是保证金口径，而 `profit_r` 是"价格距离 / R 距离"（无杠杆），两者不要混用。

### D.5 R 的定义

`R = profit_r_atr_multiple × ATR1h(入场时)`，并夹在 `[entry × profit_r_min_pct, entry × profit_r_max_pct]`：

- 用 **ATR** 而不是"入场时的枢轴支撑"：与策略其它阈值口径一致，且不引入额外的枢轴计算失败路径。
- **入场时冻结**，不在持仓期间更新：ATR 在暴跌中会放大，用当前 ATR 跟踪会让止损在下跌中**变松**——这正是 `_timeframe_reversed` 已经有的毛病，不该复制。
- **夹逼**是必要的风控：ATR 退化（横盘）时 `R` 会趋近 0，棘轮几乎一开仓就武装，等于变成一个极紧的止损。

### D.6 只读反事实影子账本（先于执行落地）

**为什么必须做这个：** README 明确拒绝回测 / Hyperopt / lookahead-analysis（强平与 OI 没有历史数据源），所以**没有任何办法**在实盘之前评估这四层的价值。影子账本是唯一可行的验证手段。

它在 `bot_loop_start`（`@decision_snapshot` 内，复用已有缓存）里逐仓维护，**与真实止损完全独立**，因此：

> **无论开关是否打开，它都给出"若启用本会在哪里退出"的结果。**

记录字段（`profit_shadow.live.jsonl`，一行一笔，平仓时归档）：

| 字段 | 含义 |
|---|---|
| `entry_price` / `entry_atr` / `r_price` | 入场上下文与 R 单位 |
| `peak_price` / `peak_profit_ratio` / `peak_profit_r` | 持仓期最高浮盈（价格 / 保证金口径 / R 倍数） |
| `last_profit_ratio` / `last_profit_r` | 最近一根完整 1h K 线的浮盈快照 |
| `actual_profit_ratio` / `actual_profit_source` | 真实平仓收益及证据来源；实盘等待交易所账本核对完成 |
| `giveback_ratio` | `peak_profit_ratio − actual_profit_ratio`，**回吐了多少** |
| `execution_lock_stop_price` / `shadow_lock_stop_price` | 实时执行棘轮与已收盘 K 线影子棘轮，两条状态互不污染 |
| `shadow_exit_price` / `shadow_exit_ratio` / `shadow_exit_reason` | 影子本会在哪里退出（`ratchet` / `stoploss` / `no_progress`） |
| `shadow_improvement` | 影子收益 − 实际收益（正 = 盈利保护更好） |
| `duration_minutes` | 持仓时长 |

**模拟的两个保守约定**（避免高估收益）：
1. **盘中顺序**：先用"本根开盘前的止损"判断是否被打到，**再**用本根高点抬升止损。即不假设"先冲高、后回落"，因此同一根 K 线内不会出现"用本根新高抬升的止损在本根被打到"这种不可能的场景。
2. **回放粒度 = `holding_timeframe`（1h）**：峰值取自 1h 高点，触发判定用 1h 低点。用 1h 高点设跟踪线对棘轮是乐观的（1h 收盘前不知道这个高点），但配对"用盘前止损判定触发"后又变回保守。

**动量条件只在最新一根 K 线上判定**，不逐根回放——因为它描述的是"当前状态"，不是历史每根 K 线的状态。（这一点在实现中被测试抓到过：早期版本对回放的每一根都套用最新状态，导致横盘 K 线被误判为"无新高"而提前触发。）

```jsonc
"profit_no_progress_new_high_r": 0.25,
"profit_no_progress_max_r": 0.5
```

**关键设计点：**

1. **`use_custom_stoploss = True` 是类属性，不是配置键。** 钩子必须始终注册，否则关闭开关时框架不会回调，打开后也不会生效。实际是否改止损由 `custom_stoploss()` 内部读 `profit_lock_enabled` 决定——关闭时恒返回 `None`，框架回退到 `self.stoploss`，**行为与接入前逐字节一致**。已用真实 `StrategyResolver.load_strategy` 验证该类属性被正确保留（并回写进 config）。

2. **`custom_stoploss` 自带 `try/except` + 失败计数 + `logger.exception`。** 框架层对本方法只打 `logger.debug`（`interface.py`），异常会导致 `adjust_stop_loss` **不被调用**、棘轮**静默冻结**——不告警就等于没有。这与已修复的 C-01 是同一类结构问题。

3. **棘轮与灾难止损共用 `trade.stop_loss`，而 `adjust_stop_loss` 只升不降**，所以棘轮在物理上不可能放松 `stoploss=-1.0` 的兜底。已实测：武装到 108 后再用 `-1.0 @ 90` 试图放松，stop 仍是 108。

4. **`profit_lock_min_step_r` 抑制改单抖动。** 框架更新交易所条件单的方式是**先撤后建**（`freqtradebot.handle_trailing_stoploss_on_exchange`），存在短暂的裸奔窗口。最小步长让每次改单都有实际意义。

5. **配置校验强制一致性**：`profit_lock_enabled` 或 `profit_no_progress_enabled` 为真时，`profit_shadow_enabled` 必须为真——否则棘轮会读到过期状态。

6. **影子 K 线回放按 1h 桶限流**：每个持仓每个完整 `holding_timeframe` 桶最多读取一次；行情暂不可用时保留重试，不会因一次读取失败跳过整根 K 线。

7. **开仓时间是影子回放的硬边界**：只处理完整位于开仓后的 1h K 线；实时 L1 直接在 `custom_stoploss` 中按当前价格武装，不借用开仓前高点。

8. **真实峰值与进度峰值分离**：`peak_price` 记录每个真实高点供棘轮使用；`progress_high_price` 只有累计推进至少 `0.25R` 才更新。连续 8 根 1h 未有效推进、趋势为 `weakening` 且当前价格低于 `0.5R` 才退出。

9. **真实武装使用持久峰值锁存**：取 `max(record.peak_price, trade.max_rate, current_rate)`。峰值一旦达到 1R 即永久武装，价格回落或进程重启都不会丢失；恢复出的目标高于当前价时保留目标但不提交无效止损。

### D.9 运行观测

1. **当前全部启用**：`profit_lock_enabled=true`、`profit_no_progress_enabled=true`；L1/L2 使用持久峰值在 1R 武装并按 1.5R 跟踪，L4 使用闭合 1h 结构并用当前价格复核。
2. **看数据**：
   - 平均 `giveback_ratio`（回吐）有多大？如果中位数接近 0，说明现有 1h 结构退出已经够用，**不要加**。
   - `shadow_improvement` 的正负比例：影子优于实际的比例是多少？
   - `shadow_exit_reason` 分布：`ratchet` / `no_progress` / `stoploss` 各占多少？
   - 特别关注 **`shadow_improvement < 0` 的那些笔**——那是盈利保护会**伤害**你的地方（典型：被棘轮扫出后行情继续走）。如果这类笔的平均损失大于收益，说明 `profit_lock_trail_r` 需要调宽或 `profit_lock_arm_r` 需要调高。
3. **持续复核参数**：重点检查 `leader_no_progress`、棘轮成交和负 `shadow_improvement` 样本；需要调节时优先调整 `profit_lock_trail_r`，不要用更低的 R 上限压缩高波动龙头的正常空间。
